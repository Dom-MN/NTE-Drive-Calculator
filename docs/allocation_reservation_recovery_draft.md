# 角色优先同分预留：低开销诊断与局部优化方案

> 临时评审/实施文档；仅供确认方案，后续可手动删除。核心递进保护、缓存、最终一对一恢复与约束复用已按本文实施；本文不替代产品文档。

## 1. 目标与边界

同分预留的目标是：前序角色可延迟确定严格等价驱动的实际 UID，后续角色可以使用其中一部分，但所有前序图纸槽位必须始终存在完整的一对一回填。恢复不能把一次局部冲突扩大为整次计算失败，也不能为了回填绕过既有的套装、形状、锁、品质、黑名单、卡带唯一性、暴击率或词条自选规则。

本方案只优化“同分回填冲突后的递进保护”路径。正常 Top-K 图纸求解、同分回填检测和最终完整一对一恢复的职责保持不变。完整阶段 3 仍只用于递进保护无法组成完整图纸的情况，不因一般分差而常态触发。

一次运行必须冻结：库存快照、角色顺序/同级组、图纸组合上限、角色权重、词条自选配置、暴击率配置、卡带选择、锁快照和取消 token。诊断、缓存和局部精修都只读这些冻结输入。

## 2. 预留关系模型

预留的最小单位是“一个前序图纸槽位”，而不是角色或驱动类型。每个槽位保存：

```text
前序组序号、所属角色、套装/散件、槽位下标、驱动类型、原始 UID、严格等价候选 UID 集
```

因此下列关系均被整体保留：

1. **同一角色的多个类型预留**：每个类型、每个槽位独立登记；最终仍回写到该角色的原槽位。
2. **多个角色共享一个候选 UID**：该 UID 在全部预留槽位间只有一个物理节点，最多回填一次。
3. **按类型分池**：仅用于重筛和匹配的性能拆分。驱动只能填自己的类型，所以不同类型无需争夺；同一类型内必须把所有前序角色的相关预留槽位放入同一次匹配。
4. **跨类型角色约束**：角色的图纸完整性、卡带、暴击率和词条自选在最终方案校验时统一检查；类型分池不能单独宣布角色方案有效。

## 3. 关键诊断日志

每个触发同分恢复的角色或同级组只在结束时记录恢复摘要与一条精修摘要；不记录 UID、完整候选集或装备 payload，也不逐轮刷屏。

```text
同分恢复：角色/组=<标识>，路径=<递进保护|最终一对一>，
常规排序分=<S0>，提交排序分=<S1>，排序差=<S0-S1>，
有效阻塞数=<N>，保护轮数=<N>，受影响类型=<类型×次数>，
前序回填=<成功|失败>，暴击/词条约束=<通过|回退>
```

### 3.1 指标语义

- `S0`：当前角色普通 Top-K 图纸中排序最优、但会使前序回填失败的完整方案的排序键。
- `S1`：递进保护后最终可提交方案的排序键。
- 排序差优先按 `stat_priority_key → rank_score → score` 解释；只有词条优先级相同时才把 `score` 差作为直观数值。
- `S0` 不代表一个可保存方案，仅表示同分回填的当前角色机会成本。
- “有效阻塞数”是实际提升前序最大回填数的被占用预留驱动数，不是所有被占用预留驱动数。

日志用于确认是否存在异常让分：保护次数高、受影响类型多且排序差明显，才说明递进路径可能损失质量。日志本身不触发最终恢复。

阶段 2 成功后额外记录一条局部精修摘要：

```text
同分精修：角色/组=<标识>，结果=<未触发|列数超预算跳过|已尝试无完整方案|已尝试无提升|已提升>，
候选列数=<类型×数量>，排序分=<精修前→提交后>，耗时=<秒>
```

## 4. 多阻塞驱动的递进保护

设最近一次完整但回填失败的当前方案占用预留候选集合为 `U`，活跃前序预留槽位数为 `R`。在扣除 `U` 后，先求最大一对一回填数 `M`，缺口为：

```text
D = R - M
```

对每个 `u ∈ U` 做小型匹配试探：临时释放 `u` 后求 `M_u`。

```text
若 M_u > M：u 为有效阻塞驱动
若 M_u = M：u 对本轮缺口无直接帮助，不进入本轮保护候选
```

一轮保护流程：

1. 从有效阻塞驱动中，按其前序所属角色的**基础权重评分**升序选择一个；同分以稳定键打破平局。
2. 该 UID 只对当前及后续候选池受保护，不视为被消费；它继续供前序槽位回填。
3. 仅重筛受保护 UID 所在的驱动类型，使用原有图纸算法生成下一完整方案。
4. 对新方案重新计算 `U、M、D` 与有效阻塞集；若仍冲突，重复本流程。

这支持多个阻塞驱动，但不会预先批量保护。每次都基于最新方案重新判断；先前无关的预留驱动不会因旧失败状态被永久排除。

因为原始前序预留状态本身存在完整匹配，只要存在缺口，逐个重新释放实际占用的相关候选会有能够提高 `M` 的有效项。若某轮没有有效项、图纸无法完整组成、保护状态重复或保护已覆盖可用冲突项，才转入既有最终恢复。

## 5. 角色 × 类型完整排序缓存与 Top-K 补足

缓存单位是单次冻结计算内的：

```text
角色 × 驱动类型 × 词条优先级层 → 全量、已排序的合法候选序列
```

缓存建立时复用已冻结的 `role_scores`，不重新计算装备评分。排序、黑名单、品质、词条自选层级和基础筛选必须严格复用普通 Top-K contract：

- 无词条自选时：按既有角色/类型排序序列；
- 有词条自选时：每个优先级深度层维护自己的有序序列；
- 零权重黑名单、普通黑名单与其他已有筛选按原 contract 处理。

某类型重筛时，从对应完整有序序列头部顺序取项，跳过：

```text
受保护 UID、前序固定 UID、已消费 UID、当前组已占用 UID
```

直到每个普通层或词条优先级层都补满 K；只有完整库存确实不足时才少于 K。这样“原 Top-K 中有驱动被保护”会自然由 K+1、K+2……候选补位，不会错误缩短候选池。

缓存只在本次冻结请求期间有效；账号、快照、权重、配置、角色顺序或取消 token 变化时一律丢弃。

## 6. 可选的阶段 2.5：小型局部精修

局部精修不是完整阶段 3，不重新枚举全部图纸，也不扫描全部类型或反复重试。它只在阶段 2 已成功后，作为一次受严格预算限制的可选质量检查。

### 6.1 触发条件

以下条件同时满足才触发；否则直接提交阶段 2 成功方案：

```text
1. 本次阶段 2 有完整可回填方案；
2. S0 与 S1 的绝对 score 差 ≥ 3；不使用相对让分；
3. 受影响类型数 ≤ 3；
4. 每个相关类型的局部候选列数 ≤ 80；
5. 本次尚未执行过局部精修。
```

阈值只限制是否尝试局部精修，不改变评分公式、普通 Top-K 或最终无解语义。超过预算时跳过，不排队、不降级为完整阶段 3。

### 6.2 固定内容与可变内容

固定：

```text
当前已选图纸、未受影响类型的当前驱动、前序固定驱动、已消费 UID、卡带选择
```

局部参与：

```text
当前角色在受影响类型中的图纸槽位
+ 全部前序角色在相同类型中的活跃预留槽位
+ 当前已选驱动
+ 缓存排序中每个当前槽位最多 5 个后备候选
+ 这些前序槽位的全部严格等价候选
```

每种受影响类型独立建一个小矩阵：

```text
行：当前角色该类型的槽位 + 前序该类型预留槽位
列：上面的局部候选 UID
边：当前槽位使用既有合法性和排序分；前序槽位仅连接自己的严格等价候选
约束：每行一个 UID；每个 UID 至多一次；前序所有行必须填满
目标：当前角色局部排序键最大
```

局部匹配允许重新考虑阶段 2 中受保护的 UID，但只有在同类型的全部前序槽位仍可填满时才能使用。合并所有类型结果后，必须进行完整方案校验；成功且排序键严格优于 `S1` 才替换阶段 2 方案，否则无条件保留阶段 2 方案。

### 6.3 暴击率和词条自选的额外规则

暴击率、卡带和词条自选会跨类型耦合，不能因为每个类型的小矩阵各自可行就直接提交。局部精修必须遵守：

1. **先保留当前图纸与卡带**，不在局部精修中随意换图纸或抢卡带；
2. 合并候选后复用现有完整校验：暴击率上限、暴击率最低值、基础暴击、专武/弧盘/好感度常驻加成、卡带主词条与副词条影响均按正式路径计算；
3. 词条自选继续使用完整 `stat_priority_key → rank_score → score` 比较，黑名单和零权重黑名单继续是原有过滤规则；
4. 任何校验失败、排序键不优或候选列超预算，直接放弃局部精修结果，保留阶段 2 成功方案；
5. 暴击率或词条自选的约束方案不可因局部矩阵找到匹配而绕过正式约束搜索。阶段 2 本身失败时，仍走现有最终约束恢复，而不是局部精修。

因此局部精修只能改善“已合法阶段 2 方案”的局部驱动选择，绝不把不满足暴击率或词条自选的组合伪装成有效方案。

### 6.4 复杂度边界

完整阶段 3 的成本包含全部图纸、完整背包和所有相关前序槽位。局部精修固定为：

```text
一张当前图纸 × 最多 3 种类型 × 每种一次匹配
```

候选矩阵超过列预算即跳过。由于只保留少量当前角色后备候选，而前序候选为保证回填正确性保留完整集合，成本由冲突类型和预留槽位数量决定，不随全部图纸组合数膨胀。

## 7. 验收矩阵

| 场景 | 必须验证 |
| --- | --- |
| 单一阻塞驱动 | 仅保护有效阻塞项，Top-K 自动补足 |
| 多个阻塞驱动 | 每轮重新计算有效阻塞集，按基础分逐个保护 |
| 同角色多类型预留 | 每个槽位独立回填，合并后角色图纸仍完整 |
| 多角色共享候选 UID | 全局唯一，不能被两个前序槽位同时回填 |
| Top-K 被保护后不足 K | 从缓存完整排序序列向后补足 |
| 暴击上限/最低值 | 阶段 2 与局部精修均不产生越界方案 |
| 词条自选、黑名单 | 排序键和过滤结果与普通路径一致 |
| 局部精修预算超限 | 跳过精修，稳定采用阶段 2 结果 |
| 局部精修可改进 | 仅在完整校验后以严格更优排序键替换 |
| 最终无解 | 当前角色 `valid=False`，前序回填和后续计算不中断 |
| 取消 | 缓存、阻塞筛选、局部匹配均响应取消且不提交结果 |

## 8. 实施顺序

1. 修正恢复摘要日志格式，并建立一次性结构化诊断字段；
2. 为预留状态提供最大匹配数和单项释放后的增益判断；
3. 将递进保护候选限定为有效阻塞驱动；
4. 建立请求级角色 × 类型完整排序缓存，并用跳过式迭代补足 Top-K；
5. 完成多阻塞、共享 UID、同角色多类型、Top-K 补足的测试；
6. 实现预算受限的局部精修；仅在阶段 2 已成功且损失达到阈值时尝试一次，超预算立即保留阶段 2；
7. 为暴击率与词条自选叠加预留冲突建立专项回归，最后运行静态检查、core、full 与取消验证。
