# 配装分配正确性：开发与验收方案

本文记录同级组分配、候选与约束一致性的原始缺陷、目标和验收边界，不代表特定账号故障的逐步复现。Calc 与独立分析组件的源码、分析组件二进制及主静态弧盘审查数据已更新；用户手工验收、专项/core/full 测试、静态检查和完整计算器重打包仍待后续。最新计算又暴露了“同级组增加一人后，其余可配成员连带失败”的未解决回归，当前问题与新增开发方案见[同级组失败隔离与补救](allocation-group-failure-isolation.md)，此前局部补救不视为该行为已验收。计算按钮经 Calc 冻结输入调用独立分析组件，不修改采集组件，也不把旧 Python 分配器当作按钮入口。已交付行为以[计算功能](../features.md#4-计算角色配置与自建角色)为准。

## 开发前核实的缺陷路径

1. `reservations.rs::choose` 在同级组部分失败时提前返回，跳过前序等价驱动的重新匹配；`run` 若回填校验失败，会把整组替换为同一个失败。这是组级结果覆盖个人可行性的直接路径。
2. `recovery.rs::partial` 优先已填套装槽和总槽数，而非合法完成角色数；`complete_partial` 保留失败角色已拿到的套装件。普通失败角色没有稳定的从零重选通道，因此可能让独立可成套者失去稀缺 UID。
3. `reservations.rs::choose` 的深层回退主要寻求完整组；完整组不可达时缺少按可完成成员选择的部分解。任何部分解仍须满足前序全部预留槽位一对一回填。
4. `solver.rs::group_fit` 在组内有显式暴击最小值时走逐槽贪心；该分支未使用传入的预留联合匹配，且可能在选完后才因暴击上限丢弃整组。`rebalance` 为词条自选交换跨角色装备时也未当场核对暴击区间，原合法匹配可能被交换后的失败覆盖。
5. 首轮候选的评分等级用于词条自选命中深度，补救阶段的 `quality_allowed` 却可能把等级变成硬准入；卡带补救也可能套用本应只过滤驱动的副词条黑名单。硬准入、自选深度和得分排序须分开。
6. Top-K 候选、图纸组合及补救束搜索均有界。零分但满足硬约束的必要形状可能不进入首轮池；有界搜索未命中不得推论完整库存数学无解。候选放宽与预算耗尽必须留下可观察状态。
7. `solver.rs::pre_tapes` 在求驱动前先分卡带；有可用卡带时，`tape_candidates` 和 `repair_tapes` 通常不枚举无卡带候选。暴击限制必须在卡带、驱动和额外驱动加成的组合上验证，不能仅凭预分卡带或单独驱动阶段判定成败。
8. Calc 的二件套图纸已经遍历四个固定套装形状的二选组合，但填充组合先按理论额外形状件数截断，随后按最终形状数量去重；独立分析组件入参时再次按相同数量签名去重。套装必要槽与填充槽的形状分工可能在实际分配之前消失。驱动只有形状，没有套装归属；套装身份只属于卡带。
9. 角色选择器对手选弧盘回退读取静态等级副属性，未统一走角色页的满级精炼一常驻投影；暴击最小值路径目前计入弧盘但不计好感；弧盘和好感均无暴击加成时自动上限返回未设置而非 100%。这些是计算来源和边界问题，不是角色真的换装。

上述结论来自静态代码路径；具体账号的当次冻结偏好及原生中间状态未被完整记录，不能据此指称其每一步根因。

## 本次源码实施状态（待用户手工验收）

Calc 已调整角色资料冻结、未知常驻与已确认零的区分、自动上限 0% 与手填 0 的传递、同名弧盘显式手选与旧配置默认名称的区分、问号说明、二件套分层图纸、同面积填充组合与同形状摆盘缓存、组合与摆盘取消检查、稳定形状遍历及一行失败展示；冻结库存能够证明必需驱动形状缺口时，会把有界搜索的笼统失败改为具体原因。静态构建器已纳入直接被弧盘精炼引用的计算目录 Buff，并递增 importer。独立分析组件已调整同级组部分解和预留回填、失败成员卡带释放、零分候选、卡带/驱动联合重试、暴击归一与品质回退、补救搜索的装备上限与总暴击率单位换算、卡带套装身份、各必要槽对及填充偏好层的有界覆盖探针，以及失败状态。驱动只按形状和角色硬约束参与必要槽或填充槽，不检查卡带的套装身份。源码与测试用例已经增补，但用户要求先自行测试，故此处不声称测试通过或发行生效。

Calc 冻结请求改为 `allocation_v1` 路由的版本 2，并要求组件声明 `allocation_v2` 能力；每个角色传 `crit_source_known` 和 `automatic_crit_cap_source_unknown`，来源已闭合时还传 `non_equipment_crit_rate`（弧盘常驻加已启用好感）。旧组件拒绝新版请求，不静默按旧暴击规则求解。分析组件已重新编译、清单已核对并放入 Calc 工作目录与既有打包目录；主静态候选已逐件审查、按基线 provenance 通过最终门禁并晋升工作目录。既有打包计算器的 Python 代码与静态库仍是旧版，完整重打包需单独处理。待用户手工验收后，再按授权执行专项、core/full、静态检查和完整 Windows 验收。
计算 worker 现冻结启动时的账号代次、账号身份、用户库路径和本次计算序号；读库前、派发前、返回前及 UI 收结果时分别复核，旧账号或同账号上一轮迟到的结果与错误回调不覆盖当前预览。启动输入采用独立副本，取消 token 按次创建，同一 controller 不并发启动第二次计算；账号切换与同账号过期回调的回归用例已增补，仍待执行。
保存阶段也改为每次复核当前 `AppContext` 的账号代次、账号身份和用户库路径，不再只读保存启动时捕获的旧对象；槽位选择弹窗返回后、后台事务检查点及 UI 回填前均检查。对应账号切换用例已增补，未运行。
新角色没有可见方案槽时，槽位选择只冻结“待创建首槽”意图，不提前执行已提交的 `create_loadout_slot`。冻结方案及身份先完成服务校验，DAO 在整批写入事务内再次确认该角色仍无可见槽、生成不冲突的正式槽键并创建首槽，然后连同其他角色方案和装备占用转移一起提交；取消、槽位变化或任一角色校验失败时，首槽和方案一同回滚。已有槽仍按原 `slot_id` 选择与锁定检查，不以显示名作为保存身份。
角色页当前弧盘及玩家纠正弧盘在 Calc 冻结时分别保留正式 `default_fork_id` 和 `effective_fork_id`；界面与旧配置仍用名称展示和保存，但同名静态弧盘若无法唯一解析，计算中止而不猜测 ID。分析组件收到的版本 2 角色数据因此带本次有效正式弧盘身份，不仅有已算好的暴击数字。

跨仓库请求只序列化本次 `role_order` 选中的角色；角色目录中未参与本次计算的条目没有冻结暴击来源，不得混入版本 2 请求导致整次计算被证据校验拒绝。该边界已补回归用例，仍待用户测试与后续授权验证。
暴击率别名识别现要求正式映射后的规范名严格为 `暴击率%`；发行数值目录中的 `暴击率`、`爆击%`、`爆击` 均映射到该规范名，未映射的原文不因字面相似而计入。暴击伤害别名保持排除；对应 Rust 回归用例已增补，暂未运行。

版本 2 原生结果增加逐角色 `budget_exhausted` 证据；图纸组合或补救分支被预算截断且该角色失败时，`search_status` 为 `budget_exhausted`，用户原因只写本次搜索未定。Calc 若能从冻结全库存证明该角色必需形状缺口，仍以更强证据覆盖为 `constraint_proven`。其他未命中保留 `bounded_unproven`。

首轮 Top-K、补救单槽候选或合法方案短名单发生截断时，版本 2 另记录逐角色 `candidate_truncated`；失败且无更强来源/约束证明或预算耗尽时，状态为 `candidate_truncated`，一行原因指出候选截断后的可行性未定。Calc 的冻结库存硬缺口证明仍可覆盖此状态。

补救束搜索的同暴击值状态桶及每规格方案输出也属于候选截断证据：状态桶由原每桶 3 个提高到 8 个，单规格从仅保留 3 个完整方案提高到 12 个，以免同级组多个高分候选都占用同一稀缺 UID 时完全抹掉可交换件；超过界限仍标记 `candidate_truncated`，不声称穷尽。
同级组卡带重试、重竞选和前序预留的部分解束宽截断同样记录逐角色候选截断，不再只记录装备 Top-K 截断。

同级补救中的无卡带候选只在本组和前序分配后没有剩余合格卡带时可作为完整结果；若仍有合格卡带只是与驱动组合超出暴击等边界，补救不得通过丢掉卡带伪造成功。组级重竞选可同时探测带卡带与无卡带图纸，但最终逐角色复核这个可用性条件，且覆盖探针分别保留这两类候选。
卡带“确实没有可分配件”的判断遍历本次完整冻结库存中的合格卡带，而不只看首轮 Top-K；补救也可从完整库存取回首轮省略的卡带，最终 UID、套装与主词条校验使用同一完整资格。否则首轮卡带截断或同级组抢占会被误写成“没有卡带”。
每组提交前再次检查无卡带完整方案：若同一冻结库存还有未分给前序或同组成员的合格卡带，则撤销该无卡带候选并进入带完整卡带池的有界补救；即使补救预算不足，也保留失败/搜索未定而非保存伪成功。
最终预留回填和 UID、图纸、暴击复核时也按整份已完成结果复核无卡带资格；有任何未分配的合格卡带而仍标记无卡带成功，应作为内部结果校验失败，不把这份结果交给 Calc 保存。
对应回归输入覆盖三个顺序组共享同一套装卡带、首轮 Top-K 仅保留两张而第三张仍在完整库存的情形：后组必须可取回第三张，不能直接保存无卡带方案；用例已加入源码，仍待获准执行。
组级束搜索还可提前剪去一种确定不成立的状态：某成员暂时无卡带，存在尚未分配的合格卡带，而剩余待搜索成员均不能使用它。其他可能由后续成员取走卡带的状态保留到全组完成后复核，避免把合法的“最后一张卡带归同组另一人”误剪掉。
前序预留的部分解恢复也采用同一规则；不能在遍历到组内第一人时，因为唯一合格卡带尚未分配就提前拒绝其无卡带方案，后续同组成员可能正好使用该卡带。该路径另补了“第一人卡带暴击超限、第二人用掉最后一张卡带、两人驱动均填满”的回归输入。
两条组级束搜索都只在本次恢复开始时计算各成员完整卡带资格；逐节点仅更新已占用 UID，不反复扫描冻结库存。前序预留恢复在跳过暴击来源不可用的成员后也重新检查暂存的无卡带状态，不让它依赖一个已经跳过的成员去消耗卡带。前序预留的深层束宽截断记录候选截断；卡带与无卡带探针即使在各自有界搜索中未触及，也不能以该次未命中断言库存无解。

Calc 先检查冻结图纸交集中的共同必需形状；即使没有共同缺失形状，只要逐张图纸都能由同一冻结候选库存证明各自的形状或硬黑名单后件数不足，也报告所有图纸均存在缺口，并给一个具体例子。具体原因与内部 `constraint_proven` 状态一同更新；存在尚未证明缺口的图纸时保留原搜索状态，避免用户文案与机器诊断相矛盾。

补救阶段的暴击包络是本次有界候选的理论上、下界，不是已经拼成完整方案的实测最高/最低值；一行原因按“候选上界/下界”表述，不把搜索中间量写成已完成结果。

同级联合恢复和前序预留的深层恢复在合法完成数相同时，也先比较二件套必要槽及填充额外形状偏好层，再比较同级词条自选键和装备得分；不能仅在首轮候选执行新偏好，回退时又退回纯得分排序。

同级组补救若仍有失败成员，不再把暂时拼成的成员锁死后只搜索失败者；已成方案也是候选，所有成员从完整可用驱动发现替代方案，再由组级束搜索重组、核对 UID 和前序预留，先比较合法完成数，再比较二件套偏好、自选与评分。候选发现共用一份组级预算：可负担时保留逐角色保底探测和公平覆盖，剩余按失败成员及其所需形状驱动或卡带的 UID 占用者倾斜，已探测而未用完的额度继续流转；暴击与预留补救也适用共享额度，约束角色优先。它既不把完整预算乘以组人数，也不让一次固定均分把难解角色锁死。首轮联合图纸组合按配置的组合数截断，补救重组另由固定束宽截断并记录候选截断。这样已成成员占用唯一形状 UID 时可以换成较低分替代件，让原失败成员完成；未发现更优合法组合则保留原暂定解。该交换仍只是有界搜索，不能据此证明全库存不可行。
例如补救探测池为 100，三人紧迫权重为 1、1、4 时先发现两名容易成员；若各实际只消耗 2 次探测，最后难解成员可使用剩余 96 次，而不是固定得到 33 次，也不会让三人各用 100 次。发现顺序不决定装备归属，候选仍按原同级组顺序参加联合重组。
部分解比较中的装备得分只统计已合法完成的成员；失败成员临时拼入的套装件或卡带既不占 UID，也不提高该组的排名。
若当前组所有失败成员的每张图纸都已被完整可用库存的必要形状缺口证明不可行，则跳过整组重竞选；这是安全的必要条件剪枝，不代替其他成员的首轮及已有补救结果。

同级组设置暴击率最小值时，首轮也不再切换到按槽顺序的单件贪心；仍用联合匹配决定 UID，并在完成整套后统一校验暴击上下限。首轮匹配若因跨件暴击约束未中，由联合补救尝试其他合法组合；不能因一个角色的逐槽优先选择直接阻断同组成员。
带前序预留的联合匹配完成后，不再执行不知悉预留关系的局部词条交换；无预留时的交换仍逐角色复核暴击边界。前序预留回填关系由同一次匹配和最终校验维持。

独立分析组件对单角色及同级组的首轮图纸先按形状、件数和角色硬资格做必要条件预检；当前候选池中合格件不足的图纸不再对每张卡带重复构造匹配，但预检不替代完整 UID 匹配、暴击判定或全库存补救。

全库存补救也先按二件套必要槽对与额外形状偏好层抽取代表规格，使用同一总预算的一半做有界覆盖探针，剩余预算再按偏好与分数顺序优化；已在探针中完整考察的规格不重复搜索。预算不足以覆盖全部代表时逐角色标记搜索截断，不能把尚未触及的低层图纸解释为库存无解。

补救产生的合法方案进入每角色有界短名单时，先保留不同偏好层、必要槽对及卡带选择的代表，再按既有偏好/词条/得分顺序补齐名额；同级部分解使用同一保留规则。不能探到了低层合法方案又在纯高分截断时丢弃它。

原生候选准备时缓存形状面积，二件套偏好判定复用这一索引；不再对每张图纸、每个必要槽扫描全部装备。形状 ID 不含面积数字时仍以冻结装备记录的实际面积为准。

弧盘来源审查以发行基线已登记的 `fork_item` 为全集，覆盖全部 51 件及各精炼等级。新候选的 22 件共有 115 条已解析无条件面板属性；24 件的每级直接引用 Buff 已入库、无直接面板 Modifier，审查为“已确认无常驻”；另 5 件仅有施加条件或伤害标签修饰器，不进入常驻面板。`fork_prism` 的五级 `CritBase` 分别为 0.16、0.20、0.24、0.28、0.32；`fork_twinbirds` 每级同时有 `MagBase` 与 `DamageUpPsycheBase`，旧版单属性主键遗漏后者。`fork_worldrain` 只有带技能/终结技标签的属性效果，不作为常驻；其等级/突破提供的 `CritBase` 仍按角色面板单独计入。完整逐件结论、精炼数值与来源计算资产记录在本次候选审查报告中。
Calc 角色投影原先仅在所选精炼等级存在常驻属性行时认定弧盘暴击来源已知，因而把已确认“无常驻”或“仅条件效果”的弧盘误判为待审查，并连带丢失其等级/突破暴击率。投影现以逐件审查状态承认这两类精炼常驻增量为已知零；有常驻的弧盘仍要求所选精炼等级存在来源行。旧 schema 无审查状态时不凭空推断零。该修复须同时更新 Calc 代码及静态库；只替换 Rust 分析组件不会生效。
重投影从已登记发行基线创建新候选，补入精炼直接引用的计算类 Buff、追加多属性 schema 与逐件审查状态，再核对未变更表逻辑指纹、基线清单及数据库哈希、来源重算、外键和 SQLite 完整性。当前工作目录的主静态库已通过该 provenance 晋升；其余原始来源不重建或假装具有新身份。未来新增弧盘仍须逐件审查；缺级、歧义或证据未闭合不生成常驻值。

计算入口的实现归属已核对：Calc 的 `src/app/facade.py::execute_allocation_inventory` 经 `src/integrations/native_allocation.py` 校验独立分析组件能力，由 `src/integrations/native_allocation_wire.py::freeze` 发出 `allocation_v1`；独立组件的 `analysis-core/src/lib.rs` 路由至 `analysis-core/src/allocation/`。该目录的 `scoring.rs` 准备候选、`mod.rs` 执行暴击边界，组级选择和恢复见同目录其他模块。采集用 `nte-core.exe` 与 Calc 旧 Python 分配器都不是该按钮算法的修改落点。

## 目标行为与实施边界

- 先求完整同级组；完整组未找到时，在明确预算内优先提高**合法完成的角色数**，再按既有词条优先级、装备得分和稳定 UID 顺序裁决。预算耗尽返回已找到的最佳合法结果，并标记搜索未定，而非声称全局最优或无解。
- 失败成员不得暂占驱动或卡带；合法部分方案逐件检查图纸、硬过滤、暴击区间、UID 唯一和前序预留回填。较高优先级组已提交结果不可被后组隐式替换。
- 首轮、逐槽选择、跨角色交换及恢复采用同一硬资格。评分等级仅决定词条自选命中深度，不排除可用于补形状的低等级装备；零权重黑名单不硬过滤，驱动硬黑名单不扩展到卡带。
- 保留现有冻结请求、取消和账号代次边界，不在 Calc 复制分析算法；失败不覆盖旧方案。组合与回退共享有界资源计划，记录搜索是否完备，避免同级组数量增大时无界枚举。
- 失败卡片只显示**一行**与本角色相关的具体原因，不使用“状态→原因→下一步”模板。内部诊断须区分已证明的硬约束不可行、当前候选未命中、预算耗尽及被其他角色占用；只有证据足以定位原因时才写具体限制，例如必需形状经硬黑名单过滤后为零件，不能把某一成员失败或前序回填失败复制给全组。
- 卡带与驱动联合选择并检查暴击区间、套装、UID 唯一及同级组竞争。若卡带专属筛选（例如主词条）后没有合格卡带，或者未设置该限制但本次确实没有可分配卡带，驱动格子填满仍是正常求解结果；沿用现有无卡带结果形态和对应缺卡带说明，不设新状态。若存在可分配的合格卡带，只是所有卡带与驱动组合均违反暴击等约束，应在搜索范围内尝试其他组合，最终无解时保留约束失败，不通过丢弃卡带制造成功方案。

## 角色资料与暴击率边界

角色资料尚未同步时使用角色功能生成的默认模板；玩家在计算优先级里手选弧盘，是纠正模板对实际弧盘的假定，不是换装，也不回写角色档案。手选弧盘按该正式弧盘的满级、最高可用突破及精炼一投影；未手选时沿用角色功能当前资料或其默认模板。计算开始按正式角色、弧盘 ID、账号代次和静态数据集冻结同一份来源；名称只作展示。弧盘常驻属性的证据审查与生成以[新版资源路线图](../roadmap.md#3-新版资源与未验证能力)和根契约为准；仅条件效果或证据未闭合时不得从模板或零值补造暴击加成，也不得把静态缺口误写成库存无解。
角色资料中若已有弧盘 ID，但本次静态目录找不到该 ID，计算资料应保持未知，不得回退毕业模板弧盘及其暴击贡献；账号或正式观测明确记为未装备弧盘时，弧盘贡献是已确认的 0，不与缺失 ID 混淆；未同步时由角色功能明确生成的默认模板仍照常使用。玩家即使手选了与当前默认弧盘同名的弧盘，也属于显式纠正，按手选的满级精炼一投影；旧优先级配置保存的默认弧盘名称本身不追认为手选。
账号角色页指向的弧盘若有常驻属性证据，但账号精炼等级缺失或对应等级没有投影记录，当前贡献仍为未知，不因其他精炼等级有记录就补作 0%；手选纠正则独立按精炼一的完整证据读取。

设 `E = 5% 基础 + 卡带/驱动暴击词条 + 实际额外驱动暴击加成`，`F = 本次有效弧盘的无条件常驻暴击率`（手选纠正时按满级精炼一，未手选时按角色资料或默认模板状态），`A = 角色功能中已启用的好感暴击率`。自动上限为 `100% − F − A`，候选检查 `E ≤ 自动上限`；玩家手填上限 `M` 时检查 `E ≤ M`，手填 `0` 仍表示不限制。玩家手设最小值 `L` 时检查 `E + F + A ≥ L`；弧盘纠正只更新 `F` 与自动上限，绝不改写最小值输入。自动上限与手动上限来源继续遵守现有最后一次操作的优先顺序；旧优先级配置迁移不换算存储数字，手填值原样显示，自动来源按纠正后的弧盘重新计算，重置行为不变。

`F` 和 `A` **已确认均为零**时自动上限为 100%，仍执行上限检查，不视为未设置；来源未知不等同于已确认零：自动来源未知时逐角色报告资料证据不足，不把上限缺失当作手填 0；自建角色明确没有弧盘时贡献已确认是零，手填 0 仍表示不限制。自动计算结果恰为 0% 时也不得复用“手填 0＝不限制”的含义，应按自动来源保留硬边界并给出相应诊断；手填 0 是保存在账号优先级配置中的显式选择，不因角色页变化改写。未手填的自动上限、以及最小值判定所用的角色贡献，随角色信息页更新并在下一次计算重新冻结；手填数值保持原样。当前最小值留空是未设置，并无自动生成最小值的实现，不从角色资料推造一个默认最小值。最小值、自动/手动上限、首轮筛选、跨角色交换和补救统一从本次冻结角色来源读取上述数值，不能在不同阶段重读角色配置或重复扣除弧盘与好感。若独立分析组件的冻结输入/协议增加字段，须按组件版本、清单及公共行为用例一起验收，不回退旧 Python 分配入口。

`E` 的统计应由同一规范化累加过程供最小值和上限使用，包含卡带实际主词条值、品质及别名归一后的暴击词条，额外形状按实际装备数量计入。当前分析组件的上下限路径分别累计词条：卡带暴击率主词条缺显式 `main_value` 时，上限路径固定回退 30%，最小值路径却按金/紫/蓝品质系数 1/0.8/0.6 回退；额外加成与副词条的别名判断也不一致。实施时在 Rust 冻结候选准备阶段一次归一每件装备的暴击值与“有暴击词条”标志，并复用同一额外形状暴击值，避免每次方案校验重复解析。显式 `main_value` 优先；缺失时以已冻结的金色暴击主词条值乘品质系数回退（金 30%、紫 24%、蓝 18%，以当次正式数值目录为准），上下限不得分别采用不同回退。别名采用现有较广的正式 `stat_alias_mapping`，且仅当精确映射结果等于 `暴击率%` 时计入；`暴击伤害%`、`暴击伤害`、`爆伤%`、`爆伤` 均不得算作暴击率，不做包含“暴击”文字的模糊判断。用金/紫/蓝卡带、有无显式主词条值、四种暴击率别名、暴击伤害别名和额外驱动暴击构造同一候选，核对上下限及暴击优先选择读取完全相同的 `E`。静态来源的 `CritBase` 小数与界面百分数只在冻结边界转换一次，避免 0.1 与 10 混用。若玩家最小值与非零手动上限在算术上直接冲突（如 `L > M + F + A`），应给出设置冲突的一行原因，不归咎于驱动库存；自动上限则始终以 100% 基准核对。

版本 2 输入若卡带暴击率主词条缺显式值，正式数值目录也未提供金色参考值，则在冻结候选准备阶段拒绝该请求，不以旧版的硬编码 30% 假定掩盖资料缺口；旧版差分夹具仍保留原回退行为。

该统一逻辑的实际落点是独立 `nte-analysis-core` 的 `analysis-core/src/allocation/scoring.rs` 候选预处理、`mod.rs::cap_ok/current` 两条约束路径及暴击优先标志，而非 Calc 的旧 Python 分配器；Calc 的 `src/integrations/native_allocation_wire.py` 继续冻结并传入正式数值与映射，不再额外复制另一套暴击判定。跨仓库协议、组件清单和公共行为用例须同步核对，组件未晋升前不能把方案文字当作已修复行为。

现状可复核的反例：假设金色卡带暴击主词条值 30%、装备缺显式 `main_value`，仅加 5% 基础暴击，紫色卡带的真实装备侧合计应为 29%，蓝色应为 23%；当前上限预计算却都当成 35%，最小值路径分别为 29% 和 23%。若副词条写作正式别名 `爆击%`，最小值路径会映射并计入，上限预计算可能漏算；`爆伤%` 则映射到暴击伤害而非暴击率，绝不因文字相近计入。常规库存若已带显式主词条数值，不会触发上述缺值回退反例；它证明两条路径存在逻辑不一致，不单独证明特定账号失败的根因。

两个问号说明只直接描述各自算式和手动设置规则，不引入新的配置术语或控件。最小值说明须包含弧盘常驻和已启用好感，明确数值只由玩家修改；上限说明须包含 100% 减弧盘与好感、手填上限及 `0` 的既有含义。

## 二件套图纸：额外形状优先的有界求解

套装必要槽固定四个，二件套只从这四个形状中选两个；四件套仍用全部四个，无效果仍不强制套装件。**四件套和无效果沿用当前硬规则：只保留额外驱动数量达到既有图纸生成最大值的组合，其余图纸不参与求解；不为库存不足回退较少额外驱动图纸。**以下分层放宽仅用于二件套。按所选两槽命中角色目标额外形状的数量分层，从多到少搜索：四槽中目标形状数为 0、1、2、3、4 时，最高偏好层分别有 6、3、1、3、6 对。高层没有合法方案才试低层；二件套目标形状优先是偏好，不是把其他合法二件套变成无解的硬过滤。

每对套装必要槽先用驱动形状、硬过滤和可用 UID 作必要条件预检；卡带另按正式套装身份和主词条筛选。再生成可摆入底盘的填充组合，优先使用**本次库存、约束及摆放均可行**的最多目标额外形状件，不足格位可用其他形状。高额外件数层无合法方案时继续较低层，不因理论形状组合的最大件数截断可行图纸。同一套装件对与填充偏好层内沿用既有词条自选优先级和基础装备评分；不再靠给二件套槽增加隐藏分决定选哪一对。最终每件分数仍用冻结的既有评分事实，额外形状带来的真实属性和暴击约束照常计算。

最高分单件只作候选排序和可证明的分数上界，不预先占用两个必要槽的驱动 UID。卡带、套装件、填充件在完整图纸内共同选取并核对暴击区间、词条自选等级、驱动黑名单、锁与同级组唯一 UID；低分但合法的件不能因高分件超暴击或被同组争用而消失。同级组先最大化合法完成角色数，再在同等完成数下比较二件套偏好层、既有词条优先级与方案得分；搜索预算耗尽只报告已找到的最佳合法方案及搜索未定，不宣称全局最优或库存无解。

性能控制不靠固定最高分或仅保留理论最大额外件数：四个槽的选对至多六种；按冻结输入缓存形状候选、装备基础分及相同总形状的底盘摆放，用面积/形状库存数量/驱动 UID 匹配作预检，以乐观分数上界剪枝并按高分先探索。图纸去重键必须保留套装必要槽与填充槽各自的形状多重集；相同总形状只复用摆放结果，不合并不同必要槽二选身份。Calc 负责图纸候选与摆放，实际按钮使用的独立分析组件负责联合选择和组级约束，两侧去重均须同步修正；不得把旧 Python 分配器当作按钮修复入口。缓存绑定冻结角色、配置、库存快照和静态数据集，组合与恢复共用取消及有界预算。

## 实施风险与验收边界

- 二件套的“目标额外形状优先”取代隐藏分权衡；新方案基础装备分低于旧算法结果是正常的目标变化，不作为阻断条件。只需在本次新目标和实际可行候选中追求更高分，逐件分数如实展示。
- 最多六个套装必要槽对不等于仅六次求解。填充组合、底盘摆放、卡带与驱动联合匹配、同级 UID 冲突可能形成乘积；六对共享一份可取消的预算与缓存，不给每对各发一份无界预算。先以有界覆盖探针为各可用偏好层争取合法基线，再按偏好和分数优化，避免首对耗尽预算导致后对完全未看；提前用必要条件和可证明的乐观上界剪枝，不以 Top-K 或最高分单件作为硬可行性证明。预算耗尽时区分“已找到合法结果”与“未证明全局最优/无解”。
- 弧盘的“已确认零常驻”“仅有条件效果”“证据未闭合”不能共用零值；手选弧盘当前只有名称和等级副属性回退，实施时须解析正式 ID 与精炼一投影。好感是否启用从同一次角色资料冻结，不能一边用模板、一边用账号实时值。
- 二件套的库存感知与偏好放宽不得改变四件套、无效果的最大额外驱动图纸硬规则；共享面积/摆放缓存可以复用，模式准入条件必须分开。
- 自动上限 0% 与手填 0 的语义不同；选择器、冻结协议和分析组件需保留来源标记或等价区分。新增来源字段或错误码按正式组件契约做版本和兼容验收，旧组件不得静默接收缺字段请求。失败或取消保留旧方案；静态资料、图纸缓存和候选池变化后重算预览，不能保存过期结果。

| 同级组一人缺件、其他人独立可拼；搜索预算耗尽 | 每人的一行原因与实际完成情况相符；搜索未定不写“库存无解”。 |
| 卡带主词条限制筛完为零，驱动可填满 | 正常返回驱动方案，沿用现有缺少指定主词条卡带的表示。 |
| 未设置卡带专属限制，本次无可分配卡带，驱动可填满 | 正常返回驱动方案；核对并沿用现有无卡带表示。 |
| 合格卡带没进入首轮 Top-K，但完整库存中的同一张卡带已分给其他角色 | 无卡带方案的说明按完整库存写“已分给其他角色”，不误写“未进入候选池”；求解资格与说明使用同一冻结范围。 |
| 有合格卡带，预分卡带与最高分驱动超暴击上限，其他组合可达标 | 联合尝试其他卡带或驱动，返回合法有卡带方案。 |
| 有合格卡带，但所有可搜索的卡带与驱动组合均违反暴击约束 | 不以无卡带方案规避约束；返回与搜索完备性相符的一行失败原因。 |
| 二件套四槽分别有 0、1、2、3、4 个目标额外形状 | 最高偏好层分别检查 6、3、1、3、6 对；在可行层内选择满足约束的高分完整方案。 |
| 两个目标形状默认成对，但其中一个形状缺合格驱动 UID | 继续较低偏好层，不把可用的另一二件套误判无解。 |
| 理论最多目标填充件数缺库存或超暴击，较少件数可拼 | 放宽填充偏好后保留合法图纸，额外属性与暴击按实际件数计算。 |
| 同一形状总数可对应不同必要槽二选，只有后一种能以唯一驱动 UID 填满 | 复用摆放计算但保留两个分配候选；选出合法二件套。 |
| 最高分套装件超暴击或被同级角色占用，次高分件可行 | 不固定最高分 UID；保留合法次高分方案和组内唯一性。 |
| 未同步角色未手选弧盘；玩家随后手选另一正式弧盘 | 前者使用角色功能默认模板；后者只纠正计算所用弧盘，按满级精炼一常驻属性重算，不写角色档案。 |
| 原弧盘暴击 10%、好感 10%、自动上限 80%；纠正弧盘为 20% | 自动上限变为 70%；手设最小值保持原数字，候选的弧盘加成只计一次。 |
| 手选与默认模板同名弧盘，但角色页当前弧盘常驻为 12%、满级精炼一为 20%，好感为 4% | 未手选用当前值计算 84% 上限；显式手选后用 20% 常驻计算 76% 上限，保存/读取后仍保持纠正；旧配置仅保存默认名称时不追认为显式手选。 |
| 最小值设置后纠正弧盘，候选配装不变 | 最小值输入数字保持原值；判断结果只因纠正后的弧盘常驻贡献而变化。 |
| 已确认弧盘和好感暴击均为零；自动上限恰为零；手填上限零 | 前者自动上限 100%，中者仍是自动硬约束，后者按既有语义不限制。 |
| 账号保存手填上限 0，随后角色页弧盘或好感变化 | 手填 0 保持不限制且存储值不变；未手填的自动上限在下次计算按更新后的角色资料重算。 |
| 最小值留空，随后角色页资料变化 | 仍不凭空生成最小值；实际弧盘和好感贡献在下次冻结时更新。 |
| 保存、读取旧优先级配置中的手填上限 70；先纠正弧盘再手填 70 | 框内仍为 70，不做数值迁移；若之后再次选弧盘，按现有最后一次操作规则重算自动上限。 |
| 弧盘条件暴击、常驻来源待审查或好感关闭 | 条件效果不进常驻；未知不伪装为零；好感关闭时不加好感暴击。 |
| 弧盘常驻来源未知且沿用自动上限；同一角色改为手填 0 | 前者仅该角色报告资料证据不足，不以未传上限产生成功方案；后者保留原有不限制语义，账号配置数字仍为 0。 |
| 同级组甲自动上限的弧盘来源未知，乙来源已确认且有唯一可用卡带和驱动 | 甲单独报告资料待审查，不占用装备；乙继续取得完整合法方案，组级匹配和最终复核都不得把甲判为成功。 |
| 同级组甲没有可摆放图纸，乙有完整图纸与可用卡带、驱动 | 卡带恢复不能把甲的无图纸占位判为成功；甲报告图纸原因，乙保留完整方案，整批不因甲缺蓝图而报终验错误。 |
| 同级组未完成成员的暂定卡带在重试中改分给已完成成员，随后补齐驱动 | 先撤销未完成成员的旧卡带引用和对应分数，再判断无卡带合法性；不得以重复 UID 使整批终验失败。 |
| 协议中确有零槽图纸，与“没有图纸”同组出现 | 前者仍冻结其图纸身份并由终验按零槽核对；后者缺少图纸身份，不能由卡带恢复伪装成成功。 |
| 金/紫/蓝暴击主词条卡带有或缺显式 `main_value`，暴击率使用 `暴击率%`、`暴击率`、`爆击%`、`爆击` | 缺值时分别按金色值的 1/0.8/0.6 计算；上下限及暴击优先共用正式别名归一后的装备暴击值。 |
| 卡带、副词条或额外加成使用 `暴击伤害%`、`暴击伤害`、`爆伤%`、`爆伤` | 均不计入暴击率；不因扩大别名覆盖面而误伤暴击上下限。 |
| 手动上限与最小值算术冲突，或额外驱动数量变化 | 前者说明设置冲突而非库存不足；后者按实际件数同时更新上下限所用的装备暴击值。 |
| 弧盘与好感贡献合计 60%、装备侧上限 40%、最小值 90%，候选装备侧为 35% | 补救搜索比较同一口径的 95% 与换算后 100% 上限，保留合法方案；最终仍用装备侧 35% 对 40% 复核。 |
| 同一冻结库存下新旧二件套排序目标给出不同基础分 | 按新目标选择合法高分方案，逐件基础分如实展示；旧方案分数更高不是本次失败。 |
| 四件套或无效果模式的最大额外驱动图纸缺库存，较少件数可填满 | 仍只考察既有最大额外驱动图纸，不将二件套的放宽策略套到这两种模式。 |
| 图纸摆盘枚举耗尽驱动件后底盘仍有空格 | 不把残缺底盘发布为完整图纸；四件套与无效果的最大额外件数准入仍保持原规则。 |
| 取消、旧快照、账号代次变化、保存 | 不写入过期或部分持久结果，旧方案保持不变。 |

## 开发落点与完成判据

按公共行为用例先行、最小业务修复、跨仓库边界验收的顺序实施：

1. 用冻结合成输入补齐上表用例，先确认当前失败及部分成功边界。用例须同时覆盖同级角色独立可行性与组级唯一 UID，不靠截图或宽泛异常文本判定；记录原有诊断改动的当前行为，不把其一行原因当成求解正确性的证据。
2. Calc 侧修正角色资料/弧盘常驻投影的读取和图纸候选、必要槽二选身份去重；保持账号配置数值、优先级顺序、方案冻结与既有无卡带结果形态。新增弧盘数据的常驻属性审查与生成遵循静态候选构建、审计和晋升流程，不能直接改发行库。若请求需携带自动/手动上限来源或其他新字段，先确定版本化协议及旧组件拒绝行为。
3. 独立 Rust 分析组件先统一装备暴击归一、卡带品质回退及准确别名映射，再修卡带/驱动联合选择、同级组部分解与前序回填、所有分配/交换/恢复阶段的资格一致性和有界搜索。每次选择结束都核对完整图纸、暴击区间、卡带套装身份、必要槽与填充槽的驱动形状、预留一对一与全局 UID 唯一；失败角色不得占件。
4. Calc 的问号与结果文案只在求解状态和内部证据明确后收口；可证明缺口写具体单行原因，候选截断或预算耗尽写搜索未定，不把组级回填失败复制为每名角色的库存缺件。
5. 分别验收 Calc 公共行为、Rust 契约与性质、跨仓库请求/响应、旧配置数字保持、取消/账号切换/保存回滚和性能预算；再依授权执行专项、core/full、静态检查、组件构建晋升及真实 Windows 复算。组件构建通过不等于 Calc 已切换到该组件，发行清单、身份、能力和哈希须另行核对。

输入域是当前账号完整库存快照、角色配置和正式静态数据集；输出域是冻结计算预览及其逐角色诊断。计算阶段不写账号方案或发行静态库；保存阶段仍只消费经边界复核的预览。取消、来源变化、组件不兼容、计算失败或保存失败均保留旧方案，临时候选与进程按既有 owner 收尾。方案中没有待用户再定的产品语义；实施中若发现与公共行为测试、正式协议或静态数据证据冲突，先记录具体冲突并回到相应责任文档裁决，不以局部补丁推翻本方案。
