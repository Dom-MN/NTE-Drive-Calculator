# 同级组单人失败不连坐：分配补救开发方案

状态：**源码已实施，专项回归与本机 CLI 回放已验证；计算器整包及用户界面实测待验收**。本文只处理计算按钮的同级组失败隔离与部分结果补救。既有暴击率、卡带、词条自选、二件套及前序预留规则仍以[分配正确性方案](allocation-correctness.md)和现行计算契约为准；这里不重新定义这些规则。

## 当前问题与证据边界

最近一次本机计算的脱敏对照是：在同一份完整库存快照、同样的前序三个优先级角色下，同级组有六人时仅一人得到完整配装；去掉其中一人后，余下五人均得到完整配装。六人请求的每角色每形状候选上限为 60，五人请求为 50；两次均有 133 件原始候选。因此这不是严格相同的求解请求，但“六人请求筛选上限更大、结果却由五人成功降到一人成功”足以暴露严重的部分结果保留问题。图纸阶段为六人均产生了合法摆放图纸，不能把其他人的失败直接解释成“没有图纸”。

这组观察**没有证明**六人能够同时配齐，也没有证明被移除的角色在完整库存中必然无解。当前常规日志只统一记录“无法凑齐合法图纸”，缺少本次原生搜索的预算、截断、单人候选与组级保底计数，尚不能给这一次失败指定唯一的内部触发点。开发时应以同一份冻结输入复核该触发点，不能根据页面失败文案推定数学无解；账号日志、真实 UID 和库存原文不进入仓库。

现有算法已经有全库存恢复、组级重竞选、共享补救预算和部分组搜索，但它们**不构成下面的结果保障**：当一个成员无法完成时，其余成员已找到的、互不抢占装备的联合方案仍应保留。此前局部优化提高了发现候选的机会，却没有把这条保障做成贯穿各搜索阶段的约束与回归验收。

### 为什么补救仍可能只剩一人

1. 首轮联合搜索检查完整组；六人图纸数在该次请求中分别为 6、12、24、27、4、24，单看图纸笛卡尔积约为 448 万种，去掉图纸数为 27 的成员后约为 16.6 万种。两者都可能超过配置的组合数上限，加入一人会改变有界候选的排列与覆盖范围。
2. 初步缺件恢复先按“填入的套装件数、总格数”挑暂定解，不以“完成多少个合法角色”为第一目标。稀缺件可能被分散给多个尚未完成的角色，后续仍需重新交换才能得到多个完整结果。
3. 最终部分组恢复**已有跳过失败角色的状态分支**，不是完全没有补救；但每人得到的搜索额度还要分给卡带、无卡带探测和驱动修补。驱动、卡带、完整方案及束状态又分别被截断。若可与其他人共存的低分替代方案在进入组级重组前被删掉，后面的“允许跳过”也找不回它。
4. 前序预留冲突后的另一条联合重试分支仍逐人只接入有效方案；某人没有兼容方案时，该分支的状态会清空。末尾虽另有部分组回退，但同样受候选覆盖与预算影响。**目前无法证明该分支是本次日志的实际触发点**，它属于应一起修掉的同类风险。
5. 部分恢复阶段没有统一的“已验证最佳联合方案不可倒退”机制；不同阶段各自算出结果再比较。早期发现的单人或多人可行方案未必作为候选进入后续重组。

易懂的例子：甲、乙都需要一种稀缺形状。甲的高分配法占用乙唯一能用的驱动；甲另有一套低几分的配法可换用普通驱动，让甲乙同时完成。若补救只留下甲的高分候选，就算束搜索愿意“跳过甲”，也只能得到一人；正确补救应保留甲的替代配法，先取得两人完整配装，再讨论分数。

## 必须达成的用户行为

- 同级组一人失败，不直接把其他成员判失败；失败成员不保留驱动、卡带或临时预留。真正完成的成员须分别满足图纸、卡带资格、品质、主词条、词条自选、暴击上下限、前序预留及全局 UID 唯一性。
- 先比较**合法完成的角色数**；人数相同时，才比较既有二件套偏好、词条优先级和最终装备得分。同级组不是按列表顺序让第一人独占装备，也不把组合预算固定均分给每个人。
- 在固定的库存、前序占用和候选全集下，加入一个无法被分配的成员，不应使其他成员已经可共同成立的结果消失。尤其是若排除其中一人能配好其余五人，六人请求至少应保留这五人的完整方案；这不承诺第六人也有解。
- “预算耗尽/候选截断未找到”与“已证明硬约束冲突”分开。没有穷尽证据时，不写库存无解或缺图纸；页面原因仍只用一行。

例一：甲、乙、丙同级，丙的套装必要形状确实缺件；甲乙的驱动和卡带互不冲突。结果应是甲乙成功、丙单独失败，而不是三人一起失败。

例二：甲和乙争同一张卡带，但乙有另一张符合主词条和暴击范围的卡带。先选两人的合法组合；不能先给甲最高分卡带，再把乙判为无解。若两张卡带均不能使乙达标，仍须检查乙的合法无卡带条件，不能用丢卡带绕过暴击限制。

例三：前序优先级角色占用一件可等价回填的驱动，同级组甲失败、乙可用该件。只有在前序全部预留槽仍能一对一回填时才给乙；若无法回填，乙的失败应说明预留竞争或搜索未定，不可悄悄破坏前序方案。

## 实施方案

### 1. 冻结组级起点和统一结果比较

进入每个同级组时固定本次完整库存、首轮候选全集、前序已占 UID、前序等价预留槽、已用卡带、角色硬约束、图纸和取消 token。各次补救尝试只能读这个起点，在选定最终方案前不改写正式占用或卡带预分配；结果经完整合法性复核后才能参与比较。

在组求解内维护一份“已验证最佳联合方案”。比较顺序为：合法完成数 → 既有偏好与词条排序 → 得分 → 稳定身份决胜。失败成员的临时填格和得分一律不计，也不占资源。新阶段没有更好结果时保留原方案；预算耗尽、取消或重试失败不得把已找到的合法成员清零。取消仍按现有请求语义终止整个计算，不提交半成品预览。

### 2. 让所有联合补救路径都能跳过失败成员

首轮全员方案失败后，继续寻找共同配装。前序预留重试与普通部分组恢复均需有两条分支：给当前成员选一套**完整合法**方案，或将该成员标为本轮未完成并继续后续成员。每条分支即时检查已用驱动 UID、卡带 UID 和预留可回填性；无卡带方案仍须符合“本组和前序分配后没有剩余合格卡带”的既有规则。不得将不同分支里各自成功的个人方案直接拼接。

例如甲没有任何可行候选，组状态仍向乙、丙继续；若乙丙可同时成立，返回“甲失败、乙丙成功”。若甲有可行候选但占了乙唯一 UID，同时尝试“甲成功、乙失败”和“甲跳过、乙成功”，再继续丙；完成数相同才按既有排序决定。

### 3. 保底候选与冲突多样性

已验证的组级联合方案、当前成员的有效配装和能释放争议 UID 的替代配装，不能只因另一方案高几分就全部裁掉。候选短名单仍保持有界，但保留依据除卡带种类、图纸偏好层、必要槽对及暴击区间外，还须覆盖“占用/释放其他成员稀缺 UID”的差异。先做形状、件数和硬过滤的必要条件剪枝，再在可行候选内排序；剪枝不能把有界搜索未触及当成硬无解证明。

例：甲的前十套都使用驱动 X，乙只能用 X；甲第十一套使用 Y。短名单若限十套，也应给“甲用 Y”保留一个代表位，而不是留下十套实际上争同一个 X 的方案。是否增加代表位、替换某个高分位，以实测候选覆盖和耗时决定；不能简单把所有 Top-K 翻倍。

### 4. 失败时做同输入的“留一联合补救”

正常全员求解成功时不触发。若同级组仅得到部分结果，从同一冻结组级起点暂时排除一名成员，对其余成员重新做**联合求解**，逐个比较结果，找到更高完整人数就更新最佳方案。达到 `组人数－1` 个完整成员时，可停止单人排除层；若连排除一人都无法改善，再利用已识别的 UID/形状冲突继续做有界部分组搜索，不无条件枚举所有子集。

本次六人反例中，留一补救试到排除图纸数为 27 的成员时，若其余五人在相同冻结候选全集中共同可行，便把那套五人联合方案作为六人请求的保底结果；被排除者单独失败。**这一步必须隔离每次尝试的卡带预分配和临时占用，最终只提交胜出的组方案一次。**

留一求解若继续使用有界搜索，它只能保证“已找到的五人方案不会被丢掉”，不能把未找到宣称为五人数学无解。为了使“手动移除一人能得到五人，六人请求也能保住五人”可对比，两种计算需采用同一冻结候选全集和同样的单次搜索额度；不能让留一尝试共享一份已经被六人搜索花光的余量。代价是失败路径最坏增加至多组人数次同级联合尝试，必须通过缓存预检、复用冻结候选、达到 `n－1` 提前停止、取消检查和实测性能控制，不能靠静默少试角色换取速度。如真实大组耗时不可接受，应先量化并重新确定产品预算与保证范围，不暗中降低上述验收标准。

### 5. 诊断与呈现

原生结果保留每名失败成员的预算耗尽、候选截断、约束证明状态，并增加不含真实 UID 的组级摘要：成员数、各阶段最佳完整人数、单人完整候选数、留一补救尝试数、是否达到预算、最终保留人数。Calc 只把有证据的一句话展示给用户；详细阶段计数进结构化本机诊断。示例：“本次搜索未找到该角色的完整配装，已保留同级组其余五人的方案。”只有冻结输入证明所有相关图纸均缺必需形状，或暴击配置本身冲突，才给出确定的具体缺口。

## 修改边界与实施顺序

1. 先建立脱敏的六人/五人冻结回归输入，并记录两个请求在同一候选全集下的各阶段完整人数、搜索预算与裁剪位置。真实账号日志和 UID 只在本机诊断，不提交到仓库。
2. 在独立分析组件的组级选择、恢复、预留重试和候选裁剪处实施统一结果比较、跳过分支与保底；失败触发的留一补救复用同一组级输入。Calc 负责冻结请求、协议适配和一行诊断，不在旧 Python 分配器里另造一套求解算法；不改采集组件。
3. 优先完成公开行为回归，再按获授权范围进行专项、组件契约、性能及 Windows 计算按钮验收。组件源码完成、二进制构建、工作目录晋升和安装包交付分开记录；本方案本身不授权编译或部署。
4. 若新算法的正常成功路径或失败补救出现性能回退，先保留旧组件包以便回退；不得以降低成功人数、忽略硬约束或把搜索未定写成无解来换速度。失败、取消、协议不兼容均保留已有持久方案，不保存未验证的部分结果。

## 验收标准

| 场景 | 必须观察到的结果 |
| --- | --- |
| 脱敏复现：六人组与排除其中一人的五人组使用同一冻结候选全集 | 若五人请求找到五人共同配装，六人请求至少保住五人；第六人是否可配另行判断。 |
| 甲单独无图纸或硬形状不足，乙丙可共同配齐 | 甲失败不占 UID/卡带，乙丙成功；不出现整组统一失败。 |
| 甲低分替代件能释放乙唯一 UID | 返回两人完整方案，而非高分甲一人；所有 UID 唯一。 |
| 前序预留与同级组竞争等价驱动 | 最终前序全部预留可一对一回填，且不为回填牺牲已经可保留的同级合法人数。 |
| 暴击上下限、卡带主词条、自选词条和无卡带资格混合 | 每个成功角色仍独立满足全部硬约束，不能通过丢卡带伪造成功。 |
| 候选或预算截断，仍已找到部分合法方案 | 返回最佳已验证方案；失败者标记搜索未定，不写库存无解。 |
| 组级某一补救分支无候选或被取消 | 无候选可继续后续成员；取消终止整次计算，不覆盖旧保存方案。 |
| 普通全员成功、上述失败补救及较大同级组 | 记录耗时和探测量；正常路径不额外执行留一补救，失败路径成本可解释且有界。 |

回归必须检验最终结果和 Calc 页面语义，而不只检验某个恢复函数返回非空。特别是“六人至少保住五人”应成为长期行为测试；只调整预算、短名单大小或错误文案，均不算完成本方案。

## 本轮实施与验证

独立分析组件已在组级选择入口加入留一联合补救：各次尝试复用同一组级库存池和前序预留，隔离临时卡带分配，达到 `n－1` 人即停止；普通部分恢复与前序预留重试均保留跳过失败成员的分支。候选短名单在原排序之外保留低 UID 冲突代表，并以已验证的联合部分结果作为后续补救保底。原生响应新增不含装备 UID 的组级人数、初轮人数、留一尝试数及恢复候选数；Calc 在失败角色旁呈现一行原因与同级组完成进度，日志仅记录汇总计数。上述变化不改变既有硬约束和持久方案保存边界。

长期合成夹具覆盖六人组与排除一人的五人组：旧组件在六人请求仅完成三人，新组件完成五人；五人请求仍完成五人，且成功方案的装备 UID 不重复。独立组件的 `allocation::` 专项测试通过 45 项；Calc→原生组件与页面呈现的专项测试通过 2 项，原生适配专项测试通过 13 项。使用本机冻结输入作不入库回放时，六人组由初轮一人提升至五人，去掉失败者的五人组仍为五人。此项回放仅是本机诊断证据，不代替用户在计算按钮上的验收；真实账号数据、UID 和日志均未写入仓库。未执行 core/full 套件。

CLI 已构建并按组件清单与 SHA-256 放入 Calc 仓库组件目录、打包目录和本机运行目录，三个副本一致；覆盖前的组件与清单保留在本机备份，供回退。当前只替换了 CLI，Calc 的 Python 页面源码变化要进入后续完整应用打包后，才会体现在既有已打包程序的界面上。
