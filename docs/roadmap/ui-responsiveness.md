# 页面切换与确认操作卡顿治理方案

状态：本轮代码已接入，角色页、基础权重、工作台和计算目录已完成隔离专项；性能及一致性前后对比见
[响应性验证记录](../validation/ui-responsiveness.md)。交付行为以[功能契约](../features.md#页面响应性与后台任务)为准。
core/full、构建、真实同步、三主题与混合 DPI 的整应用人工验收尚未执行；不标记所有页面卡顿已解决。

## 1. 目标与范围

目标是同时减少重复工作和主线程阻塞，让页面切换、保存和重置期间仍可正常重绘、滚动及处理输入。
继续使用现有 Qt Widgets，不更换 Qt 版本，不修改评分公式、分配算法、Core/DLL 协议或游戏操作规则。
第一轮集中处理角色页、基础权重和工作台摘要；其他入口先测量，再按证据处理。

安全要求不是“后台执行即可”，而是新旧业务结果一致、草稿不丢失、账号不串用、最新配置不会被旧回调覆盖。
只有性能指标和这些行为门禁同时通过，才认定本方案完成。

## 2. 改动前确认的阻塞路径与证据

| 路径 | 改动前行为 | 为什么会卡 |
| --- | --- | --- |
| `src/ui/main_window_navigation_mixin.py` | 切换页面后直接调用页面刷新 | 刷新函数结束前，事件循环不能及时处理重绘和输入 |
| `src/features/official_role/role_shell.py`、`controller.py` | 进入角色页清空并重建索引、标签页；当前角色详情同步读取 | 查库、图片路径查找、配装上下文准备和控件创建叠加在一次 UI 回调中 |
| `src/services/official_role_page_service.py` | 索引和详情重复准备资源目录；详情包含库存及多槽位上下文 | 每次进入都重新承担未变化数据的成本；替换候选等重数据未充分按需加载 |
| `src/features/configuration/page.py` | 保存/重置后直接调用 `_load_data()`；重置还同步重建权重表单 | 数据已经保存，但用户继续等待整个计算目录及表单刷新 |
| `src/ui/main_window_data_mixin.py` | 计算目录源键包含账号库和 WAL 文件大小、修改时间 | 无关写入也使目录失效；读取完成后又遇到文件变化时，会丢弃结果并再次刷新 |
| `src/ui/controllers/inventory_sync_controller.py` | 满足状态条件时调用同步的 `_refresh_home()` | 同步状态变化可能触发摘要查库和差异读取，首页隐藏时也承担成本 |

本轮已有本地计时样本：一次角色索引读取约 734 ms，紧接着详情读取约 1652 ms，合计约 2.39 秒，
尚未计入后续控件创建和绘制。近期 20 次详情读取中位数约 494 ms，最长约 2.75 秒。
这是已确认的优化对象，不代表每次卡顿都由同一条路径造成，也不是所有设备的统一耗时。

仓库、配装和计算页面的数据读取已有后台路径，不重复推翻；这些页面若仍慢，优先检查结果应用、控件重建和重复请求。
SQLite 存在最长约 10 秒的忙碌等待配置，但本轮证据尚未证明实际卡顿来自锁等待，不全局缩短超时。
现有游戏性能指标不覆盖 Calc UI 事件循环，具体范围见[性能指标契约](../reference/performance-metrics.md)。

## 3. 核心处理方式

### 3.1 页面先响应，数据随后到达

页面切换的主线程回调只做导航、加载状态和轻量控件更新。查库、文件访问、静态目录解析和页面数据整理交给
该功能 Controller 管理的后台任务，Service 返回与 Qt 控件无关的页面模型。

- 首次进入展示页面框架和“正在加载”，数据完成后显示内容；未加载完成的业务操作暂时禁用。
- 同账号再次进入，未失效内容直接复用。已失效内容可保留只读旧展示并标识更新中，禁用依赖它的操作。
- 加载失败保留已有持久数据和草稿，提示重试；首次失败不把未知内容显示成空库存、零属性或正常结果。
- 用户离开页面后，只读结果可丢弃；再次进入时按有效版本复用或重新请求。

例如：从计算切换到角色，即使角色详情仍需后台读取 1 秒，窗口也先显示角色页和加载状态，用户可以返回或切换
其他页面；不是让窗口冻结 1 秒，也不是把没有读取到的配装当作“无配装”。

后台线程自行打开、使用和关闭 DAO；不把主线程的账号 SQLite 连接交给 worker。静态 DAO 的现有共享机制须核对
线程契约，按正式读取入口处理，不仅通过关闭线程检查来共享连接。控件及 QPixmap 创建仍在主线程，后台只返回
普通数据、路径或经线程契约允许的图片数据。

### 3.2 减少重复读取和整页销毁

角色页保留已有页面骨架和标签容器，按正式 `character_id` 更新索引。未变化角色不反复删除再创建；切换角色只加载
该角色详情。后台返回新模型后更新必要部分，不用整页重建来刷新一个字段。

数据分三层管理：

1. **静态展示资料**：角色名称、图标路径、成长/技能静态结构，以已校验 dataset 与资源清单身份缓存。
2. **账号页面模型**：面板、槽位、装备汇总，按账号、代次、角色及实际依赖版本缓存；不能仅以角色名称为键。
3. **较重的替换候选**：进入对应功能时才准备，不因打开基础角色页就读取整份候选库存。

常用面板和现有配装汇总仍正常显示，不能为了加速把整个 `include_inventory_contexts` 关闭而使已有功能缺数据。
应将必要的已装备上下文与可延迟的候选池分开读取。替换功能准备期间保持明确的加载状态，完成后才启用确认操作。
未展开区域可延迟构造控件，但保留原先的入口、结果与键盘可达性，不悄悄删除信息。

例如：只修改某角色好感度，刷新该角色面板及相关汇总，不重读其他角色的图标、技能目录和全体配装。
若变化的是全局家具加成，所有依赖面板标记失效；当前角色立即更新，其他角色在查看时更新。

缓存保持有界：轻量详情初始最多保留最近 8 个角色；整库存候选不塞入这些详情缓存，只归对应活动任务所有。
账号切换及 dataset 更换释放相关缓存。淘汰数据缓存不删除未保存草稿，也不销毁仍由任务持有的冻结输入。
不引入常驻全角色预加载，不把卡顿变成后台持续占用 CPU 和内存。

### 3.3 计算目录失效改为“业务内容改变”，不是“数据库文件动过”

保留文件变化作为保守的变化探针，但不再把整个库/WAL 的时间戳直接作为完整目录是否可应用的唯一依据。
通过组合根注入窄的变更通知，提交成功后标记相关数据域待校验；通知不是持久事实的替代品。

| 变化 | 应更新的内容 |
| --- | --- |
| 角色权重保存或重置、工坊模板更新 | 权重表单及计算评分目录 |
| 角色养成、弧盘、家具变化 | 有效角色面板及依赖该面板的配置/展示 |
| 配装槽位、锁、装备状态或完整库存变化 | 对应配装/库存模型及下一次任务输入 |
| 历史记录、战报或其他无关表写入 | 不因为文件时间变化而重建全体计算角色卡 |
| 账号、代次或静态 dataset 变化 | 相应缓存整体失效 |

具体采用“本机会话通知 + 后台窄校验”，首轮不增加数据库 schema：

1. 已知保存入口提交成功后推进对应会话版本，立即使消费者待更新。
2. 页面进入或启动业务前发现库/配置文件有变化时，后台读取该目录真正依赖的配置字段，生成规范化内容指纹；
   使用一致性读取边界，明确字段集合及排序，避免无关行顺序造成假变化。
3. 指纹未变就复用完整模型，指纹变化才重新准备目录。不在主线程读取或哈希整库，也不每帧轮询。
4. 新模型按账号代次、请求身份和语义指纹校验后应用；无关 WAL 写入不再仅因时间戳变化使模型反复重建。
5. 若存在未归类写入或直接外部改库，由保守探针触发上述校验，不只依赖 UI 通知。写入依赖字段的正式入口须
   全部接入通知；实际任务仍由 Service 冻结本次数据库与配置输入，不把页面缓存当作新的数据事实源。

例如：后台保存一条战报，不重建角色权重卡；把暴击权重从 1 改为 2，则必须更新，下一次计算使用新值。
已经开始的计算和已产生的预览仍使用原冻结权重，不重新解释旧预览和历史评分。
目录尚未更新完成时不启动依赖它的新计算，禁止以“保持响应”为由使用已知过期的权重。

本轮实现的依赖清单还包括原生角色观察、已观测角色 ID 和资源清单。窄字段在账号 DAO 的一致性事务中读取；
跨连接目录组装前后复核相关字段身份，相关写入最多重读一次，持续变化则提示重试，不回放无关 WAL 写入。
纯角色拼音排序键在后台准备并有界缓存，避免首次绘制角色卡时初始化拼音字典。

此项先枚举 `_read_allocation_catalog` 的全部实际依赖再实现指纹；宁可保守地多刷新一次，不漏掉套装、额外形状、
自建角色、弧盘或默认模板更新。持续相关写入时合并后续请求，忙碌状态下不无限新建 worker。

### 3.4 保存和重置不再同步刷新整个计算页面

基础权重保存、重置和角色保存由 Controller 冻结本次输入并在后台调用现有 Service。
保存成功后更新本页必要内容、发出变更通知，由消费者异步更新；移除页面对 MainWindow 私有 `_load_data()` 的直接调用。
重置仍按现有确认语义处理草稿、当前角色和默认来源，不借本次优化改动用户规则。

保存必须分清两个结果：

- **数据库提交成功**：可以提示保存成功、清除本次已保存的脏标记。
- **后续展示刷新失败**：表示刷新失败，保留已提交数据；不把它解释为保存失败并自动再写一遍。

例如：用户点击保存后，按钮显示保存中，提交完成即确认保存；计算目录在后台更新，期间窗口仍可操作，
但新计算等待目录准备完成。保存失败则留在原页并保留输入，不能先清空草稿再报错。

特别处理“离开页面时先保存”：现有离页确认是同步布尔返回，不能简单异步化后直接返回允许离开。
改为导航保存一个明确的待去目标，保存提交成功且账号代次仍匹配时才执行这一次导航；失败留在原页。
重复点击不产生重复写入或多次跳转。取消离页保持现有规则。
保存中冻结输入并禁用本 owner 的重复提交及冲突编辑，不全窗口禁用。账号切换和关闭通过现有生命周期门禁等待
写任务终态；事务提交后不强杀线程，不用取消承诺撤销已提交数据。

保留现有事务及错误契约；若既有写入流程不是整体事务，不通过“异步成功”掩盖部分提交，也不在本轮暗中扩展跨 DAO
事务。开发前审查保存失败后的真实状态，保持准确反馈及恢复入口。

### 3.5 首页摘要按变化合并，隐藏时不做重查询

同步状态标签保持实时更新；摘要查询与状态文案分离。

- 完整库存快照、角色同步版本或摘要实际依赖发生变化才标记摘要待刷新；相同版本的监听状态不重复查库。
- 首页不可见时只标记待更新，不读取完整差异；返回首页立即请求最新摘要。
- 首页可见时首次变化立即请求；已有请求期间只保留一个最新待办，不逐事件创建任务。
- 持续变化时最多按约 500 ms 的合并窗口调度后续刷新；任务未结束则不重叠执行。
- 暂态错误和业务状态仍及时展示，不因为摘要合并而延迟错误提示。旧结果不覆盖已确认的新版本。

例如：连续多次收到同一背包版本的“监听中”，只更新轻量状态，不重复比较两份库存；玩家真正更新装备后仍刷新
摘要。首页隐藏期间发生多次变化，返回时读取最新状态一次，不回放整个事件队列。

### 3.6 防止“后台读完，前台又卡一次”

记录结果应用阶段，按测量处理重控件创建、布局和图片加载：

- 不变化的控件、选择、展开状态和滚动位置保留；仅变化内容更新。
- 控件数量较大时分批应用，单批以约 8–12 ms 为初始预算，测量后调整；主线程事件循环在批次间恢复。
- 分批完成前整份模型仍未业务就绪，依赖完整结果的操作保持禁用，不把半建好的 UI 当成完整输入。
- 每批复核请求和页面身份；离页、取消或新请求使剩余批次失效，不能向新页面继续追加旧控件。
- 不使用循环 `processEvents()`、嵌套事件循环或主线程 `wait()` 来假装异步，避免重入提交和状态错乱。

若后台纯 Python 计算仍因 GIL 竞争造成 UI 延迟，先减少/缓存工作并测量；不把每项任务无限开线程，也不预先引入
新的进程池。只有测得明确的 CPU 瓶颈，才另行评估隔离计算的必要性。

## 4. 全部异步路径的安全约束

1. 请求冻结账号、generation、路径、静态身份、角色/槽位、实际来源快照、配置身份与取消 token。
2. 每个功能 owner 最多一个活动读取及一个最新待办；明确区分读任务和提交任务。
3. 结果回调和分批应用都核对身份。账号切换后旧结果不能更新新页面、新服务或新账号库。
4. 缓存模型与编辑草稿分离。自动同步、新模型到达和缓存淘汰不覆盖未保存输入；冲突继续走现有确认规则。
5. 页面刷新不触发保存、重新计算、极速装配、锁定/弃置或其他游戏写操作。
6. 只优化本机读写编排，不修改 Core 超时、RPC 重试或外部动作幂等性。
7. 新 owner 使用公开 `close/stop` 生命周期；关闭不在主线程做无限等待，也不释放仍被 worker 使用的对象。
8. 旧展示只能用于展示，不用于已知过期的新操作；历史方案及运行任务的冻结事实不因缓存失效而改写。

## 5. 实施顺序与文件边界

| 顺序 | 开发内容 | 完成条件 |
| --- | --- | --- |
| 1 | 在现有操作计时基础上补 UI 回调、结果应用和事件循环延迟的低频观测，建立基线 | 能区分读取、构造、绘制等待和锁等待；不记录完整用户输入 |
| 2 | 角色索引/详情后台读取，缓存静态资源，复用页面骨架，延迟替换候选 | 角色页无主线程重读取；草稿、面板、各槽位及替换结果不变 |
| 3 | 权重/角色保存与重置后台编排，离页保存串接，计算目录语义校验 | 保存后新权重可靠生效；旧任务/预览不变；失败不丢草稿 |
| 4 | 首页摘要后台加载、去重及可见性合并 | 同步保持监听，摘要新鲜且无隐藏页重复重查询 |
| 5 | 根据计时压缩结果应用及布局成本，完成专项与人工验收 | 主线程性能目标和行为门禁同时满足 |

优先改现有 Controller、Service 和页面接线，不按功能名随意增加模块。窄依赖由组合根显式注入；不增加服务定位器、
跨 Feature 私有调用或挂在 MainWindow 上的共享后台状态。权重页面接近行数上限，触及时先收缩/迁移编排至其现有
Controller，新增及修改 Python 文件遵守仓库 800 行门禁。
仓库、配装及工具已有 worker 的入口保持其接口与来源规则，只在测得应用阶段瓶颈时进行针对性调整。

## 6. 验收：证明真的变快，而非把卡顿隐藏起来

### 6.1 性能对比

同一机器、同一匿名测试输入、同一构建条件下，分别记录优化前后：

- 冷启动首次进入与热状态重复进入；角色、权重、首页切换各重复至少 30 次。
- 同步关闭及保持监听两种情况；记录角色数、库存规模及所用 dataset 身份，不记录私有明细。
- 导航/确认 UI 回调耗时、事件循环延迟、后台读取耗时、结果应用耗时、完整重建次数、worker 峰值和内存趋势。
- 操作速度及窗口重绘两者分别评估：后台总加载时间不能冒充 UI 卡顿时间，单次最好成绩不能代替 P95。

首轮验收目标是：普通热状态切页/确认回调 P95 不超过 50 ms，页面框架可响应的反馈在约 150 ms 内出现，
不由本轮路径造成持续超过 200 ms 的事件循环阻塞；已确认的角色加载主线程工作时间相对基线下降至少 70%。
这些是待验证目标，不是已实现承诺；冷加载完成时间可以更长，但期间须保持可操作。

未变化热状态不重建索引、整页或完整计算目录，仅允许必要的窄校验。连续操作不产生无界任务队列；反复进出同一页
后任务和页面对象能释放，内存达到稳定区间而不是每轮上涨。若读线程改善后应用阶段仍超标，继续收缩该阶段，
不只展示加载动画就宣称已解决。

### 6.2 必须通过的行为场景

| 场景 | 必守结果 |
| --- | --- |
| 同一数据优化前后读取 | 角色属性、汇总、权重、配装各槽位及候选结果一致；业务排序规则不变 |
| 保存/重置权重后立即进入计算 | 新任务使用新权重；当前优先级、勾选和配置按原规则保留 |
| 计算运行中修改配置 | 已冻结任务、预览与历史评分不被新配置重写 |
| 修改角色但不保存，再离页或同步更新 | 保存/放弃/取消行为不变；未保存草稿不被后台结果覆盖 |
| 离页选择保存，期间重复点击 | 只提交一次；成功后只导航一次；失败停留且保留草稿 |
| 角色读取中切换角色/账号/静态目录 | 旧回调和旧应用批次被丢弃，不串页、不串账号 |
| 新快照或锁变化发生在加载期间 | 新操作重新取得有效冻结输入，不用失效缓存执行 |
| 保存失败、查询失败或模拟库占用 | UI 保持响应，持久数据不被展示刷新覆盖，错误反馈准确 |
| 连续切页和持续同步 | 各 owner 并发有界；首页能最终显示最新版本，无无关事件刷新循环 |
| 关闭窗口/账号切换 | 生命周期有界收尾，无仍运行线程被销毁、跨账号提交或丢弃已提交写入 |
| 三主题、键盘与混合 DPI | 原有操作可达，加载/错误/禁用状态可辨，内容不被遮挡 |

默认不执行编译或测试。开发获准后再按用户授权范围运行专项；core/full、打包与真实 Windows 验收分别申请或取得
明确授权，分别记录证据。没有完成的项目如实保留，不以源码接入替代验收。

## 7. 风险控制和回退

- 分阶段提交，每阶段保持业务输出不变；若性能收益不达标或行为门禁失败，不继续扩大到其他页面。
- 本轮不更改账号 schema、不清库、不改方案内容，也不增加持久页面缓存，因此回退不依赖账号数据迁移。
- 回退只撤销本轮代码及接线，保护其他开发者改动；已经合法提交的用户配置正常保留，不恢复整份旧账号库。
- 测量和差分使用隔离输入；账号活库备份遵守 SQLite 一致性备份规则，不复制活动 WAL/SHM。
- 新路径验收后移除旧同步 UI 调用，不长期维护新旧两套入口；Git 保留回退依据，不新增永久“双模式”开关。

最终交付标准：用户切页和确认不再等待整页重查、重建，同时业务结果、数据来源、冻结身份、保存语义和外部操作规则
保持原契约。性能未达标或关键行为未验收时，不标记为已解决。
